# Offline EAGLE compiler

Start here when asking an AI assistant to build a new PCB. The assistant can define the schematic,
board, and routing constraints in a JSON spec, then compile, route, preview, and validate the design
with Fusion closed. This avoids repeated calls to Fusion while the assistant iterates. Use MCP to
import the reviewed candidate as a new linked Electronics Design, run native checks, and make
targeted edits in Fusion.

The compiler is available in server version `0.4.0`. Candidates generated by
`0.3.0+workflow.35` still load with their original manifest hashes.

## Compile, route and review from the CLI

Install the base package from the repository root with `python -m pip install .` and make sure
`fusion-electronics-mcp` is on `PATH`. Run this PowerShell example from the repository root. It
prepares the [LED switch fixture](../tests/fixtures/compiler/minimal/design.json) in a fresh
temporary directory and selects all five nets for routing.

```powershell
$fixture = (Resolve-Path ./tests/fixtures/compiler/minimal).Path
$work = Join-Path ([IO.Path]::GetTempPath()) "fusion-compiler-$([guid]::NewGuid().ToString('N'))"
New-Item -ItemType Directory -Path $work | Out-Null

$spec = Get-Content -Raw -LiteralPath (Join-Path $fixture design.json) | ConvertFrom-Json
foreach ($asset in (@($spec.templates.schematic, $spec.templates.board) + $spec.libraries)) {
    $asset.path = Join-Path $fixture (Split-Path -Leaf $asset.path)
    $asset.sha256 = (Get-FileHash -Algorithm SHA256 -LiteralPath $asset.path).Hash.ToLowerInvariant()
}
$spec.routing.selected_nets = @($spec.nets.name)
$specPath = Join-Path $work design.json
[IO.File]::WriteAllText($specPath, ($spec | ConvertTo-Json -Depth 30))
$specHash = (Get-FileHash -Algorithm SHA256 -LiteralPath $specPath).Hash.ToLowerInvariant()

$base = fusion-electronics-mcp compile-candidate --spec $specPath --spec-sha256 $specHash `
    --output-directory (Join-Path $work candidate-base) | ConvertFrom-Json
$job = fusion-electronics-mcp route-candidate --manifest $base.manifest_path `
    --manifest-sha256 $base.manifest_sha256 | ConvertFrom-Json
$job.preview_path
$job.diagnostics
```

Open the routing preview and inspect the diagnostics, then publish the saved routing result and
review the final candidate.

```powershell
$final = fusion-electronics-mcp route-candidate --manifest $base.manifest_path `
    --manifest-sha256 $base.manifest_sha256 --job-manifest $job.manifest_path `
    --job-manifest-sha256 $job.manifest_sha256 --output-directory (Join-Path $work candidate-routed) | ConvertFrom-Json

$preview = fusion-electronics-mcp render-candidate --manifest $final.manifest_path `
    --manifest-sha256 $final.manifest_sha256 | ConvertFrom-Json
$validation = fusion-electronics-mcp validate-candidate --manifest $final.manifest_path `
    --manifest-sha256 $final.manifest_sha256 | ConvertFrom-Json
$preview.preview_path
$validation.report | Select-Object status, airwires
$final | Select-Object manifest_path, manifest_sha256 | ConvertTo-Json
```

Expect `status: pass` and `airwires: 0`. Open the final HTML preview to inspect the schematic and
board. Keep the printed manifest path and hash together for [Fusion import](#import-one-reviewed-candidate).

For your own design, use a fresh output directory and replace `$specPath` and `$specHash` with the
absolute path and SHA-256 of your prepared spec. The planner uses `routing.selected_nets` unless
you supply one or more `--net NAME` arguments. An empty selection can produce a passing job with
zero routing work, so check `report.airwires` as well as `report.status`. If you skip routing,
use `$final = $base` for review. A base candidate with required full routing can return exit code
3 and still provide a manifest for planning.

Planning stores jobs under `routing-jobs/<job-id>/job-manifest.json` in the base candidate's parent
by default. Use `--output-directory` to choose a different parent. Promotion takes both job pins and
a fresh output directory, and uses the selection already saved in the job.

## Prepare a design specification

1. Export an empty flat EAGLE schematic and its empty board as UTF-8 EAGLE XML. Use matching EAGLE
   XML versions and keep the normal layers, classes and board design rules. The schematic needs
   sheets with no parts, instances, nets, buses or module instances. The board needs empty element
   and signal containers and no existing copper. Use a board template whose copper stack matches the
   design. Declare the outline, holes and keepouts in the specification.
2. Export each approved library to a local EAGLE XML `.lbr`. Pin each library and template by
   absolute local path and exact file SHA-256. On Windows,
   `(Get-FileHash -Algorithm SHA256 $path).Hash.ToLowerInvariant()` gives the pin. The library name
   identifies it in the specification. Select exact deviceset, device, technology and gate names
   from that library. The compiler resolves physical pads through the EAGLE gate and pin mappings
   and embeds the selected definitions.
3. Start with the complete [LED switch example](../tests/fixtures/compiler/minimal/design.json) and
   its adjacent `empty.sch`, `empty.brd` and `project.lbr`. Replace its fixture paths with absolute
   local paths and recompute the pins from your copies. The [version 1
   schema](../server/fusion_mcp/data/offline-design.schema.json) describes the JSON fields. Use
   `"version": 1` and `"units": "mm"`. Declare sheets, part placements, and nets by explicit part,
   gate and pin. Use `"schematic_style": "wired"` for local connections and `"labels"` with an
   explicit `"inter-block"` or `"inter-sheet"` port where needed. Set `routing.require_fully_routed`
   to `true` to make unjoined board contacts block import. The [routed
   fixture](../tests/fixtures/compiler/e2e/design.json) shows that policy and per-net routing
   limits.
4. Save the spec as UTF-8 JSON without a byte order mark and hash that exact file. Keep the manifest
   paths and SHA-256 values returned by the compiler and use those pins for subsequent operations.

The board template supplies the default placement grid. The compiler tries nearby grid points
when the requested PCB position conflicts and records any off-grid routing-clearance exception
in validation. Set `off_grid: true` on a board placement to keep its exact coordinates. Fixed
placements and pads with explicit preroutes stay at their declared positions. Set `align_50mil`
to `true` to explicitly configure a 50 mil (1.27 mm) grid in both exports and align schematic
symbols to it. Supply an explicit `ref` for a part named in nets or placement overrides. Use
`ref: null` to allocate the library device prefix for a part without those references.

## Read the validation report

| Exit code | Result |
| --- | --- |
| 0 | Pass |
| 2 | Invalid input, including unreadable paths or mismatched hashes |
| 3 | Failed or unverified |
| 4 | Budget-limited partial routing |
| 5 | Internal error |

The candidate manifest pins the EAGLE pair, validation report, routing intent and review artifacts.
`render-candidate` verifies the published files and returns the path to `index.html`.
`validate-candidate` verifies the pins and returns the published report. A finding of `fail`
identifies a detected violation. `unverified` means the offline checks could not establish the
result. A required finding with either status blocks import. A partial job can be promoted for
review, and the resulting candidate must pass all required validation to qualify for import.

`report.airwires_by_net` shows how many joins remain between contact groups on each net, based on
traces, vias, and pads. For each net with a nonzero count, check `report.planes`. An open on a net
without a pour needs routing. A pour whose plane status is `unverified` needs a native refill and
connectivity check. With `routing.require_fully_routed: true`, opens awaiting fill verification can
make the required `full_routing` finding `unverified` and block import.
For a design that intentionally relies on native pours to make connections, use
`routing.require_fully_routed: false` for that candidate and review every open before import. All
other required checks still apply. After import, refill the polygons in Fusion and check the plane
connections and remaining airwires before accepting the board.

## Routing limits and saved jobs

Declare an intentional Fusion differential pair in `routing.matched_pairs`, for example
`[["CLK_P", "CLK_N"]]`. List the exact positive and negative net names in that order.
The compiler preserves these names in the schematic and board. Preflight flags undeclared board nets
with complementary `_P` and `_N` suffixes, which Fusion recognizes as a pair. For ordinary analog
polarity, use `CT1_POS` and `CT1_NEG` or other names that avoid the automatic pairing suffixes.
The offline router plans each net independently. Route or adjust critical pairs as a pair in Fusion
and verify the spacing and length match with Fusion's
[differential-pair tools](https://help.autodesk.com/cloudhelp/ENU/Fusion-ECAD/files/ECD-DIFF-PAIR-CPT.htm).

Routing uses the policy pinned in `routing.budget`. It preserves protected nets and subdivides
selected same-net traces at tees so every branch ends at the same emitted point. Via landings use
the via center. Readback checks require shared serialized trace endpoints, with pad centers
rounded to the board writer's precision. The board template supplies fabrication rules such as `rvViaOuter`,
`rlMinViaOuter` and `rlMaxViaOuter`. The compiler writes the 25%, 8 mil and 20 mil defaults
respectively when the template omits them.
Per-net `allowed_layers` limits traces. Set `via_spans` to the full-stack endpoint pair
(for example, `[[1,16]]`), or to `[]` to forbid through vias. Through vias check clearance on
every layer they cross, including any reserved reference plane. A pre-routed pad-to-via escape
can serve as the launch point for an inner-layer routing job.
The router uses the greater of the board width minimum, net class width, and any per-net
`min_width_mm`. Enter power widths after sizing the shared segments for combined load and copper
thickness. Preflight rejects narrower traces, overlapping collinear runs, and drill spacing below
the board's `mdDrill` rule. Same-net annulus overlap is reported separately from drill spacing.

`board.keepouts[].layers` accepts enabled copper export IDs, including inner layers.
The compiler emits a layer-41 RestrictCopper mask for a keepout that includes inner copper.
Layer 43 remains a separate via-only restriction. If a pour outline crosses a copper keepout,
offline candidate validation reports it as unverified. Guarded import requires that check to
pass. The four-layer harness checks saved Fusion contours separately on its disposable fixture.
The job records the selected connections, the proposed board, diagnostics and a review preview,
including useful results when some connections stop early. Inspect termination reasons, attempted
layers, via usage and reported blockers before changing your constraints. Planning with the same
pinned request can reuse its published job. Promotion verifies the source candidate and job hashes
and copies the saved result to a new candidate without rerunning the search.

| Budget field | Default | Maximum |
| --- | ---: | ---: |
| `max_nodes_per_attempt` | 200,000 | 1,000,000 |
| `max_nodes_per_connection` | 300,000 | 2,000,000 |
| `max_attempts_per_connection` | 2 | 8 |
| `max_seconds_per_attempt` | 15 | 60 |
| `max_seconds_per_job` | 600 | 1,800 |
| `max_vias_per_connection` | 2 | 8 |
| `ripup_rounds` | 2 | 8 |

Search allocation is also capped at 8,000,000 states. Limits bound work on difficult geometry and
keep retries from silently changing the approved routing policy. Adjust the spec and compile a new
candidate if you choose to change a limit or placement.

## MCP workflow

Call `get_offline_compiler_workflow()` for the installed schema path, workspace and limits. On
Windows the workspace is `%LOCALAPPDATA%/fusion-electronics-mcp/offline-compiler`. On macOS it is
under `~/Library/Application Support/fusion-electronics-mcp/offline-compiler`. On Linux it is under
`${XDG_DATA_HOME:-~/.local/share}/fusion-electronics-mcp/offline-compiler`. For MCP outputs, use
relative paths under that workspace or absolute paths contained in it, with existing parents. Use
the returned absolute paths and hashes to pass results to the next tool.

1. `compile_eagle_candidate(spec_path, spec_sha256, output_directory)`
2. `plan_eagle_candidate_routing(manifest_path, manifest_sha256, selected_nets=None, output_directory=None)`
   optionally saves a job. The default output parent is the compiler workspace.
3. `promote_eagle_candidate_routing(manifest_path, manifest_sha256, job_manifest_path, job_manifest_sha256, output_directory)`
   optionally publishes the saved job as a new candidate.
4. `render_eagle_candidate(manifest_path, manifest_sha256)` and
   `validate_eagle_candidate(manifest_path, manifest_sha256)` verify the candidate for review.
5. `import_eagle_candidate(manifest_path, expected_manifest_sha256, request_id, project_id, name, folder="")`
   imports one reviewed passing candidate.

## Import one reviewed candidate

Use the final CLI `manifest_path` and `manifest_sha256` from the example, or the values returned
by the offline MCP tools. MCP can read the CLI candidate in its original location on the same
machine. If you want to review it through MCP first, pass those same values to
`render_eagle_candidate` and `validate_eagle_candidate`.

Connect to the running Fusion add-in 0.14.23 or newer. Save all open Fusion documents and clear
pending edits and dialogs. Activate the destination project and call `list_designs()` to get its
`project_id`. Generate a fresh 32-character lowercase hex request ID with
`[guid]::NewGuid().ToString('N')` in PowerShell. Choose an unused product name and an existing
project-relative folder path, or use `""` for the project root.

Call `import_eagle_candidate` with these arguments, replacing the placeholders with your values.

```json
{
  "manifest_path": "<final manifest_path>",
  "expected_manifest_sha256": "<final manifest_sha256>",
  "request_id": "<generated request ID>",
  "project_id": "<project_id from list_designs()>",
  "name": "LED Switch",
  "folder": ""
}
```

The importer rechecks the pins and offline validation before staging the exact pair. It verifies
the original documents and destination, the imported pair's electrical signature, and the saved
family's links and identities. `saved_linked` includes the saved native IDs.

Each call can advance one native step. A resumed request performs at most one orchestration status
read. The guarded picker helper performs its own preflight reads before a file submission. For
`pending`, follow `next_action` when present and call the same tool again with identical arguments.
On Windows the tool can submit the owned native pickers one at a time. On other platforms, select
the returned staged schematic and then the staged board in Fusion before resuming. Reuse the request
ID throughout, including when retrieving a saved result.

A recorded `state_unknown` ends automation for that request. Inspect the existing ticket with
`get_eagle_pair_import_status(request_id)`, check Fusion for a pending picker or error dialog, and
inspect the open documents and target folder for a new or partially saved family. Keep the same
request ID while investigating. Resolve the existing ticket before starting another import.

## Native acceptance

The compiler supports flat designs and through vias. Hierarchical EAGLE modules, automatic part
acquisition or substitution, blind or buried vias and arbitrary native slot verification are
outside its supported checks. Plane connectivity requires measured native fill. After import, run native ERC and DRC
and review their findings. Refill and check polygons where applicable, inspect placement,
footprints, routing and the 3D view, and verify manufacturing and datasheet requirements
independently.

The live acceptance harness is opt-in and writes to the supplied disposable Fusion project. Run it
from the repository on Windows with the authenticated add-in, an explicit disposable project ID and
an unused product name. The harness checks the imported family's identity and name uniqueness before
closing it through Fusion's name-based native close. It then reopens by the pinned saved product ID.
The report records offline validation, native ERC, post-repour airwire endpoints, measured fill
connectivity, native rule and restriction readback, and native DRC separately. It compares
serialized trace and via geometry at five decimal places and checks routing policy again after
refill. Exported layer-19 spans are compared with live endpoints for diagnosis. Pass `--artifacts PATH`
to save the report and exports under a new directory.

```text
python tests/live/e2e_compiled_import.py --disposable-project-id ID --name NEW_PRODUCT
```

Add `--inner-restrict` to run the four-layer fixture and compare the two inner-layer restrictions
after native reopen and export. For an existing passing compiler candidate, supply both
`--manifest PATH` and `--manifest-sha256 HASH` in place of the fixture selection. If its offline
report leaves connections pending on unmeasured pours, the live run checks their repoured
contours and still requires zero native airwires.

Live acceptance is pending an explicit disposable project ID and new product name.
